# ccweb 产品与 Harness 诊断（2026-10-30）

## 用户目标与结论

用户明确要求改善自动模式、计划模式、运行一切模式，补齐 Skills、Commands 设置，以及各类配置的分类管理 UX；以本机 DeepSeek Harness 和 Claude Code 终端的实际操作为参照。

当前 ccweb 有真实 Claude Agent SDK 桥接、对话渲染和指标展示基础，但配置管理与任务生命周期尚未形成可靠的产品闭环。优先做「可正确控制的本地 Claude Code 工作台」，再在同一执行基础上补配置实验与回归能力。保留现有 React/Vite、Hono/WS 和 AgentSession，不在本轮更换运行时或引入 DSH 插件架构。

最影响使用的三项问题：

1. **配置和运行事实不一致**：新会话未传入已选模型与权限模式；纯净档未按 SDK 契约禁用文件系统设置；设置重启丢失。
2. **配置页面缺少管理闭环**：没有自动模式与 Commands 管理页；Skills 仅列出部分本地目录并标记启用；来源、作用范围、覆盖关系和生效时机不清楚。
3. **任务缺少稳定归属与恢复语义**：重连后可见审批却无法处理；全局事件缓冲与连接内注册表作用域不一致；崩溃后消息排队但执行未重建。

## 缺陷与功能差距

证据等级：页面/服务实测为真实应用行为；模拟复现为服务与桥接代码行为；静态核验说明代码边界，不能外推模型表现。

| 编号 | 优先级 | 发现 | 证据与影响 |
| --- | --- | --- | --- |
| B01 | P0 | 新会话不使用已选择的模型、权限模式 | 模拟捕获 `query.options`：设置 `audit-selected`/`plan` 后，两字段仍未传入。`agent.ts` 的初次 `query()` 缺少两项；热切方法并不能覆盖尚未启动或后来新建的会话。计划和完全权限的运行行为未获真实验收。 |
| B02 | P0 | 「纯净」档与锁定 SDK 契约不符 | 模拟捕获 `settingSources` 为省略。锁定 SDK `sdk.d.ts` 明确说明省略加载默认来源，空数组才禁用文件系统设置。不能据此承诺已经隔离所有记忆、MCP、插件或环境变量。 |
| B03 | P0 | 重连审批无法处理 | 模拟运行触发审批 → 关闭 WS → 新连接请求重放 → 审批可见 → `permission.resolve` 返回 `permission_not_found`；再 `session.open` 仍不能处理原审批。原 pending 未解决。 |
| B04 | P0 | 事件重放没有会话/连接隔离 | 模拟另一连接 `ping(lastSeq:0)` 可收到原连接审批。`index.ts` 的 ring/seq 是全局，AgentSession 注册表却在每个连接内部。此处反映多窗口串事件与所有权错误，不等同于远程泄露结论。 |
| B05 | P0 | 崩溃后的重试缺少恢复 | 模拟 SDK 抛错 → 服务发 `agent_crashed` → 再次发送 → 消息停留队列，没有重新创建 query；`started` 和活动状态没有退出收敛。错误中的 `retry:true` 缺少对应可用恢复路径。 |
| B06 | P1 | 设置在服务重启后丢失 | 真实服务设置 model/plan/effort/none/workspace → 重启 → 恢复 null/full 默认值。应持久化应用自己的默认值，并区分当前会话实际值。 |
| B07 | P1 | 切工作区后旧任务失去当前控制入口 | 模拟等待中的任务 → `workspace.set` → `interrupt`：旧任务未 abort，也未收到 interrupt。处理分支直接清空 `currentSession`；应明确继续后台执行或取消，不能只把引用丢掉。 |
| B08 | P1 | MCP 状态错误使用数组下标为名称 | 锁定 SDK 契约返回 `McpServerStatus[]`；模拟 `[{name:'audit-mcp',status:'connected'}]` 经现有 `Object.entries` 转成名称 `0`。错误又被空结果兜底，用户难区分失败与无配置。 |
| B09 | P0 | 打开设置触发持续读取循环 | 真实页面在设置开启后 500ms 内发出 473 次 `settings.get`（隔离小配置目录中的本次采样，不是性能基准）。`App` 每次渲染传入新 `send` 函数；SettingsModal 的 effect 依赖 `send`，应答更新 settings 又使 App 重渲染。真实用户配置更多时还会反复扫描磁盘。 |
| U01 | P1 | 自动模式缺失，其他模式直接展示内部枚举 | 页面只有 `default/acceptEdits/plan/bypassPermissions`；真实协议拒绝 `permissionMode:'auto'`。锁定 SDK 类型已有 `auto`，但能否实际启用仍需能力与账号/模型条件验证。 |
| U02 | P1 | Skills 是目录展示，不是完整管理 | 仅扫描全局 `~/.claude/skills`；界面统一显示「全部自动生效/已启用」。没有项目/插件来源、正文管理、禁用能力判定、冲突处理和运行实际载入反馈。 |
| U03 | P1 | Commands 没有设置页 | 仅扫描用户和项目 `commands` 顶层 `.md` 并提供补全；并非新建、编辑、参数、嵌套命名与来源管理。内置命令也没有独立的 GUI 操作契约；输入文本仍交给 SDK，不应假设所有 TUI 命令都能照常工作。 |
| U04 | P1 | 设置分类和有效值解释不足 | 当前 6 个分类为模型/端点/权限/Skills/规则/MCP；模型页混入上下文隔离，缺少 Commands/Hooks/配置诊断。生效展示主要读全局文件，而运行时热切和模板覆盖使用另一组值。 |
| U05 | P1 | 首次使用没有真实就绪判定 | 无凭证的隔离用户目录仍显示「完整 ~/.claude 配置已就绪」。当前 UI 没有补齐自定义端点和凭证的完整首次设置路径，主要依赖预先存在的 cc-toolkit 模板。 |
| H01 | P2 | 轨迹和指标不足以支持 Harness 调优 | 协议没有稳定的 run/request 归属、完整终态、配置快照与版本、验收结果；没有可复现配置实验和一组任务的比较报告。现有会话、事件和指标可复用，但不能把这些展示等同于实验闭环。 |
| Q01 | P1 | 当前质量门无法保护核心体验 | `pnpm check` 不包含 E2E，server 单测只覆盖指标。CI 的 E2E job 限定 `workflow_dispatch`，但 workflow 没有声明该事件；4 个浏览器用例也仅覆盖外壳，当前有 2 个失败。 |

额外的静态边界：

- 消息级 fork 按钮实际调用会话末尾 fork，未传消息位置，不能称为任意历史消息处分叉。
- 「总是允许」按工具名放行，不是具体命令/路径规则；审批未接入超时和取消收敛，`PermissionGate.replay()` 没有接入重连控制流程。
- 服务重启后能读取 SDK 历史文件，不代表运行中进程、待审批、队列和中断控制可恢复。
- 500 条环形缓冲不是持久运行日志；客户端也没有完整的服务 epoch、事件去重与缺口重建策略。

## 按用户任务重新组织界面

沿用当前控制台视觉和技术栈，优先修正可用性、信息架构和行为。主界面保留当前工作区、运行模式和任务状态；设置采用以下分类，支持搜索，内容较多时用可定位的设置页面替代窄小弹窗。

| 分类 | 用户在这里完成什么 | 必须解释的边界 |
| --- | --- | --- |
| 通用 | 语言、主题、密度、启动和通知偏好 | 本应用偏好，不改 Claude 全局配置 |
| 模型与连接 | 配置端点、凭证、模型映射和 effort，检查连接 | 已保存/已测试/当前运行值分开；凭证只写或遮罩，不通过快照回传 |
| 运行与权限 | 选择手动、自动、计划、运行一切，审查允许/拒绝规则 | 当前会话与未来默认值分开；自动评估不等于跳过全部审批；SDK 不支持时禁用并说明 |
| Skills | 查找、阅读、管理用户/项目/插件技能，确认可调用方式 | 来源、只读性、实际加载、名字冲突、原生支持的启停范围 |
| Commands | 管理自定义命令、参数和说明，使用内置命令 | 内置只读；自定义可编辑；GUI 动作、SDK 可执行命令和暂不支持的 TUI 行为明确区分 |
| 上下文与规则 | 查看 CLAUDE.md、规则、记忆来源和上下文设置 | 文件系统设置来源不是完整安全隔离；显示继承、覆盖和适用工作区 |
| 工具、MCP 与 Hooks | 检查连接/工具能力/Hook 配置与失败原因 | 配置存在、可发现、已加载、可调用是不同状态；先诊断，按原生能力逐步增加管理 |
| Harness 实验 | 保存配置方案，跑代表性任务，检查轨迹并比较结果 | 配置版本、输入与工作区版本、真实验收和开销可关联；回放事件不等于重新执行 |

共同交互要求：每项配置显示来源、作用范围、默认值、覆盖值、运行实际值和生效时机；编辑有保存/取消、校验错误、重置覆盖和写入冲突提示。默认只写 ccweb 自有配置；修改 Claude 用户/项目文件必须明确目标文件、预览差异、保留未知字段、原子写入并可恢复。不假设插件技能都能直接改写或逐项关闭。

## 与本机工具的对照及取舍

- 本机 Claude CLI 支持 `auto/plan/bypassPermissions` 等权限入口；ccweb 应给中文标签与解释，并以 SDK 当前能力和执行回执显示实际状态。计划模式还需要计划正文、采纳/修改/拒绝、执行转换的完整流程，单独加一个枚举不够。
- 本机 DSH 文档把未来默认权限与当前会话权限分开，设置读取/提交有版本和错误反馈；这些交互原则值得采用。
- DSH 的命令有专门的执行/弹窗/输入表面，Skills 有来源与调用展示；ccweb 目前偏重补全和目录列表。先补用户能完成的任务，不逐项照搬 DSH 的插件包体系。
- DSH 的 preset/插件配置能力依托其运行时。ccweb 的实验方案先组合现有 SDK 暴露的模型、权限、配置来源、工具与预算，不承诺 DSH 的任意插件、调度或循环策略都可移植。

详细实现门槛见 [SPEC.md 的当前 Stage 计划](../SPEC.md#2026-10-30-当前-stage-计划)。

1. **Stage 5：模式与运行可靠性。** 修复 B01–B09，首先停止设置读取循环；配置保存/生效可核对，自动模式按实际能力开放，计划/运行一切不以 UI 选中代替运行事实；刷新和审批可回到同一任务；崩溃、取消、切工作区都有明确终态或后台归属。

3. **Stage 7：Harness 实验闭环。** 同一执行与审批基础上提供无 GUI 调用例、配置快照、运行记录和小型回归任务集；比较完成率、失败类型、真实验收和 token/耗时/成本，不仅画图。
